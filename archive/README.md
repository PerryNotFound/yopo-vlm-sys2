# 归档：开发历程中的探索原型

本目录保存 M2（候选轨迹语义否决）最终方案 `eval/m2_veto.py` 定型之前的所有探索版本。
**这些文件不再维护，仅供参考与论文"方案演进"小节使用。**

## 文件清单

| 文件 | 思路 | 为什么被取代 |
|---|---|---|
| `vlm_closed_loop.py` | 最早闭环验证：VLM 逐帧判断，直接发 `/cmd_vel`（安全前进/危险停车） | VLM 推理 ~1Hz 太慢，看到危险时车已碾上；绕开规划器导致抖动 |
| `vlm_m2_veto.py` | 图像切左中右三块分别问 VLM，改写 `/cmd_vel` 左转/右转绕行 | 切块 resize 失真 + 小区域理解差，树影误判为泥；直接改速度绕开规划器 |
| `m2_arbitrator.py` | 仲裁节点：转发或截停 MPC 的 `/cmd_vel` | 成为控制链瓶颈，小车左右摇晃 |
| `m2_projected.py` | 整体/分区判断后向安全方向发 `/vlm_goal` 目标点 | `/vlm_goal` 是软约束：YOPO 只把它当方向参考，argmin 仍可选穿水轨迹 |
| `m2_real.py` | 把 5 条候选轨迹投影回图像，逐条截 100×100 区域问 VLM | VLM 对小区域理解差；可视化红色轨迹线干扰判断，所有轨迹全判危险 |
| `m3_vlm.py` | 左中右威胁判断 + 连续 2 次确认的状态机，发 `/vlm_goal`（注：命名与论文实验 M3 撞车，实为 M2 的探索原型） | 同 `m2_projected.py`：软约束无法真正改变选路；硬编码 path_1=左/path_3=右，但候选轨迹是网络无序输出 |
| `vlm_node.py` | "方案 A"完整部署节点：VLM 输出像素坐标 → 深度反投影 → `/vlm_goal` | 同上，目标点软约束机制本身不成立，被 `/vlm_veto` 硬否决架构取代 |

## 最终方案的改进点（对应各原型的教训）

`eval/m2_veto.py` 相比以上原型：

1. **硬否决替代软引导**：`yopo_node` 新增 `/vlm_veto` 接口，被否决候选代价置 +inf，从机制上保证不选危险轨迹（解决 `m2_projected`/`m3_vlm`/`vlm_node` 的"YOPO 不听"）
2. **方向靠几何不靠序号**：按轨迹末端方位角 + 相机内参投影判定区域（解决 `m3_vlm` 的序号硬编码）
3. **整图单次推理替代切块**：全图上下文减少树影误判，且快 3 倍（解决 `vlm_m2_veto`/`m2_real` 的小区域问题）
4. **颜色定位 + VLM 语义确认的 hybrid 模式**：VLM 不做空间定位（其弱项），只做二值语义把关（解决左右混淆、区域抖动）
5. **恢复状态机**：全否决时经 `/vlm_goal` 引导扇区转向安全方向——此时否决兜底，软引导才真正可用
